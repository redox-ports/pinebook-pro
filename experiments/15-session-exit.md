# Experiment 15 — Session exit: kernel-generated signals vs sender credentials

**Date:** 2026-11-21
**Goal:** after the desktop session ends (the user pressed **Super-Q**, which
orbital maps to `quit_front_window`), the login window never came back — the
panel disappeared and only the wallpaper stayed. The serial log ended with:

```
[src/procmgr.rs:2071 ERROR] failed to send SIGCHLD to parent PID ProcessId(34): Operation not permitted
```

**Related:** experiment 13 (orbital desktop image), `patches/base/README.md`,
`orbutils/src/orblogin/main.rs` (the login loop).

## What the log shows

Two `funmap passed length` warnings (the dying client unmapping its heap), then
the SIGCHLD failure, then nothing. The machine itself stayed alive — `ohcid`
keeps ticking, the kernel does not panic — so this is a userspace accounting
problem, not a hang of the system.

The same line appeared once before, on an earlier desktop run
(`logs/serial-20261121-191859.log`, `[ 157.6]`), with the same lack of any
follow-up activity at the login layer.

## Root cause

When a process exits, procmgr runs the `AwaitingThreadsTermination` state for
it (`bootstrap/src/procmgr.rs`). After the last thread is gone it reports the
exit to the *parent*:

```rust
if let Some(parent_rc) = self.processes.get(&ppid) {
    // When a process exits, the parent is sent SIGCHLD.
    if let Err(err) = self.on_send_sig(
        current_pid,                 // <-- the exiting process is the "caller"
        KillTarget::Proc(ppid),
        SIGCHLD as u8,
        ...
```

`on_send_sig` then applied the generic `kill(2)` sender-credential rule:

```rust
if caller_euid != 0
    && caller_euid != target_proc.ruid
    && caller_ruid != target_proc.ruid
{
    return SendResult::LacksPermission;   // EPERM
}
```

On the Pinebook Pro every session ends across a uid boundary: `orblogin` runs
as **root** (it has to — it calls `setns`/`apply_login_schemes` and reads
`/etc/shadow`) and spawns the session as **`user`**. So the exiting session
process (euid 1000) "sent" SIGCHLD to a parent with ruid 0, the check rejected
it, and the exit notification was dropped.

That is wrong at the level of the model, not just on this board: the SIGCHLD
on exit (and the `SIGHUP` procmgr sends to a newly-orphaned process group, and
the SIGCHLD that relays a child's stop/continue to its parent) is generated by
the **kernel side of procmgr**, not requested by the exiting process. POSIX
does not subject it to `kill(2)` permissions — Linux delivers SIGCHLD
regardless of the child's credentials.

## Fix (`patches/base/bootstrap/src/procmgr.rs.patch`)

`on_send_sig` gained a `kernel_generated: bool` parameter, and the credential
check became:

```rust
if !kernel_generated
    && caller_euid != 0
    && caller_euid != target_proc.ruid
    && caller_ruid != target_proc.ruid
{
    return SendResult::LacksPermission;
}
```

All five procmgr-originated call sites pass `true` (the exit SIGCHLD, the two
orphaned-pgid SIGHUPs, and the two stop/continue SIGCHLD relays); the eleven
call sites that forward a real userspace `kill`/`send_signal` request keep
`false`, so the userspace permission model is unchanged. Userspace cannot
reach the bypass: the flag lives entirely inside procmgr.

## Why the parent cares

`orblogin` is a loop (`orbutils/src/orblogin/main.rs`):

```rust
loop {
    match login_window(...) {                 // login UI, one winit run
        Ok(Some((mut command, username))) => {
            /* apply_login_schemes, setns into the user namespace */
            match command.spawn() {
                Ok(mut child) => match child.wait() { ... },
                ...
            }
            /* setns back, drop the user namespace */
        }
        ...
    }
}
```

so the login window returning after a session is exactly "run the loop body
again". The EPERM desynchronised that loop from the session lifetime.

## Open question

procmgr wakes the parent's blocked `waitpid` through `waitpid_waiting`
independently of the signal: the exit path inserts the status into the parent's
`waitpid` map and drains its waiter queue, and `work_on`/`on_waitpid` then
resolve the blocked request. That means the EPERM alone does not explain a
`child.wait()` that never returns, and `orblogin` may instead fail *after* the
wait returns — the namespace restore (`setns(...).expect(...)`) or the winit
event-loop reuse in `login_window`. Both paths log only to stdout, which
`init`'s `nowait VT=3 orbital …` sends to VT3, i.e. **not** to the serial
console, so the log cannot tell us which happened.

If the login window still does not return with this fix, the next step is a
temporary `/scheme/debug` write in `orblogin` (the kernel debug scheme *is*
serial, and `debug` is in `DEFAULT_SCHEMES`) so the next hardware run shows
where the loop stops.
